# Security

## Secret management

- No secret is ever committed to Git. `.gitignore` excludes `*.tfvars`
  (except `*.tfvars.example`), `.env` (except `.env.example`), and Terraform
  state files.
- The database password is generated by Terraform (`random_password`,
  32 characters) and written only to Azure Key Vault. It never appears in
  Helm values, Kubernetes manifests, GitHub Actions YAML, Dockerfiles, or
  application source.
- Application pods retrieve credentials at runtime via the [Secrets Store
  CSI Driver](gitops.md) using Azure AD Workload Identity - a federated
  OIDC credential scoped to a specific `(namespace, service account)` pair,
  not a stored password or service principal secret.
- CI/CD authenticates to Azure using OpenID Connect federation
  (`azure/login@v2` with `client-id`/`tenant-id`/`subscription-id` GitHub
  Actions *variables*, not secrets) - there is no Azure credential stored in
  GitHub at all, federated or otherwise, beyond the app registration's own
  federated-credential trust relationship with this repo.

## Identity

- **AKS control plane identity**: user-assigned managed identity, used for
  cluster-level Azure operations (load balancer, disks, route tables).
- **Kubelet identity**: user-assigned managed identity used by nodes; the
  only permission it holds is `AcrPull` on the container registry.
- **Workload identity**: user-assigned managed identity federated (via the
  AKS OIDC issuer) to the `backend` and `postgres` service accounts in each
  namespace. Holds `Key Vault Secrets User` only - it can read secrets, not
  manage the vault.
- No service principal passwords/client secrets are used anywhere in this
  project.

## Kubernetes workload security

Every container in `kubernetes/helm/{backend,frontend,postgres}`:

- Runs as a non-root, explicit numeric UID/GID.
- `allowPrivilegeEscalation: false`, all Linux capabilities dropped.
- `readOnlyRootFilesystem: true` for the frontend and backend (an
  `emptyDir` is mounted at `/tmp` for anything that needs to write). Postgres
  needs a writable data directory so it does not run read-only root, but
  still runs as a non-root user with capabilities dropped.
- Explicit CPU/memory `requests` and `limits`.
- `livenessProbe` + `readinessProbe` on every workload, plus a
  `startupProbe` on the backend and postgres to tolerate slower cold starts
  without flapping.
- `NetworkPolicy` resources restrict traffic to what's actually needed:
  postgres only accepts connections from pods labeled
  `app.kubernetes.io/component: backend`; frontend/backend only accept
  ingress from same-namespace pods and the ingress controller's namespace.

PostgreSQL's `Service` is `ClusterIP` only - it is never assigned a public
IP or exposed through the ingress. There is no path from the Internet to the
database that does not go through the backend API.

## RBAC

- Application workloads use per-component `ServiceAccount`s (not
  `default`), each with no bound `Role` beyond what the CSI driver / kubelet
  needs - the application containers themselves never talk to the
  Kubernetes API.
- Argo CD's own RBAC is scoped by `AppProject` (`argocd/projects`): its
  `destinations` whitelist is limited to the `dev`, `staging`, `prod`, and
  `argocd` namespaces on the in-cluster API server.

## Network

- Hub/spoke VNets with an explicit NSG on the AKS subnet denying inbound
  Internet traffic by default (Azure Load Balancer traffic for the ingress
  controller's public IP is a separate, managed path, not a subnet-level
  inbound rule).
- Azure CNI Overlay + Azure network policy at the AKS layer, plus
  namespace-level Kubernetes `NetworkPolicy` objects at the workload layer.

## TLS

- Ingress TLS is terminated by NGINX using a certificate issued by
  cert-manager against a Let's Encrypt `ClusterIssuer` (staging or prod
  directory) - see [gitops.md](gitops.md) and
  [deployment.md](deployment.md) for exactly what this requires (a real DNS
  name pointed at the ingress controller's public IP). It is **not** enabled
  in the default `dev` values, since a demo cluster rarely has a real domain
  attached; enabling it is one values change once you have DNS.

## What this project does not do (and why)

- **No AAD group-based RBAC on the AKS API server.** Left out to keep the
  demo reachable with a single `az aks get-credentials` call. In a real
  production cluster, enable AKS-managed Azure AD integration and bind
  `Role`/`ClusterRole`s to AAD groups instead of relying on the cluster
  admin credential.
- **No private AKS API server by default** (`private_cluster_enabled` is a
  module variable, defaulted to `false`). Set it `true` for a stricter
  posture; doing so requires a jumpbox or VPN into the VNet to reach
  `kubectl`, which is deliberately out of scope for a portfolio demo.
- **No egress firewall.** The NSG blocks inbound Internet traffic; it does
  not restrict what cluster nodes can reach outbound. Azure Firewall in the
  hub VNet is the natural next step and is exactly what the hub's shared
  subnet is reserved for.

## Supply chain security

Every image `docker-build-push.yml` builds is signed and gets an attached
SBOM before the GitOps handoff commit happens:

- **Keyless signing** ([cosign](https://github.com/sigstore/cosign)): no
  signing key is generated or stored anywhere. `cosign sign` uses the
  workflow's own GitHub Actions OIDC token to get a short-lived certificate
  from Sigstore's public Fulcio CA, tying the signature to the exact
  workflow/repo/ref that produced it - the same OIDC-over-stored-secret
  pattern already used for the Azure login in this workflow.
- **SBOM** ([syft](https://github.com/anchore/syft), SPDX format):
  generated from the pushed image by digest (not by tag, since tags are
  mutable) and attached as a signed in-toto attestation (`cosign attest
  --type spdx`), plus uploaded as a GitHub Actions build artifact for
  ad-hoc inspection.
- Both the image build (`az acr build`) and the signing/SBOM steps
  authenticate to ACR via `az acr login`, itself derived from the same OIDC
  session as the Azure login step - no ACR admin credential or Docker
  registry password is stored in GitHub at any point.

Verify a signature yourself (requires `cosign` locally):

```bash
cosign verify \
  --certificate-identity-regexp "https://github.com/<your-org>/<your-repo>/.github/workflows/docker-build-push.yml@.*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  <acr-name>.azurecr.io/aks-platform-backend:<tag>
```

A Kyverno admission policy checks this same identity/issuer pair at
deploy time - see "Policy as code" below.

## Policy as code

[Kyverno](https://kyverno.io) is installed cluster-wide by
`scripts/install-kyverno.sh` (same script-installed pattern as
ingress-nginx/cert-manager - see [gitops.md](gitops.md)). Unlike the
controller, the policies themselves are GitOps-managed
(`argocd/applications/platform/kyverno-policies.yaml`), since policy changes
are exactly the kind of thing worth a PR review. Three `ClusterPolicy`
objects live in `kubernetes/policies/`:

| Policy | Enforces | Action |
|---|---|---|
| `require-resource-limits` | every container declares CPU/memory requests and limits | Enforce |
| `disallow-latest-tag` | no pod uses an image tagged `:latest` | Enforce |
| `verify-image-signatures` | backend/frontend images carry a valid cosign signature from the identity above | Audit |

The first two are `Enforce` immediately - this repo's own charts already
satisfy them (explicit resource limits everywhere, immutable git-SHA image
tags always, never `:latest`), so there's no real risk of blocking a
legitimate deploy. `verify-image-signatures` starts as `Audit` (report-only,
same reasoning as Trivy's `exit-code: "0"` below) because it depends on the
`<your-org>/<your-repo>` placeholder in that policy actually matching your
fork - flip it to `Enforce` once you've confirmed it passes.

## Running a security scan

`.github/workflows/security-scan.yml` runs on every PR and weekly:
Gitleaks (secret scanning), tfsec (Terraform static analysis), and Trivy
(container image vulnerability scanning, uploaded as SARIF to GitHub code
scanning). None of these block merges in this reference setup (`exit-code:
"0"` on Trivy) - tighten that once you're past the initial buildout.
